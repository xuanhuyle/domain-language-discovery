## 0. Scope, method and limits

**Inputs read in full.** README.md, CHARTER.md, RESEARCH_PROTOCOL.md, CLAUDE.md, DECISION_LOG.md, research/01-discovery/CANDIDATE_TEMPLATE.md, prompts/01-discovery.md, prompts/02-adversarial-review.md, prompts/00-charter-protocol-review.md, the PR #1 title and body, the branch diff against `origin/main` (main holds README.md only), and the GitHub repository description, which reads exactly `finding a new programming language`.

**Method.** Thirteen independent reviewing lenses were run against the documents: one per required critique dimension A–J, plus a cross-document consistency audit, a solo-founder execution walk-through, and a bounded first-party reference check on existing engines. Every defect each lens raised was then attacked by three independent refuters (textual accuracy against the files, realism of consequence, quality and cost of the proposed fix). Of 110 raised defects, 71 survived; the 39 dropped were overwhelmingly duplicates of surviving defects or concerns another document already contains. Survivors were clustered by root cause into fifteen clusters, ranked, and turned into 50 consolidated amendments. Every BEFORE anchor in the amendments file was verified verbatim with `grep -F` against the branch head (51 of 51 matched). The lead reviewer then re-read every finding below against the source text.

**Epistemic labels.** Throughout, **observation** = verifiable in the documents, with the passage quoted; **judgment** = the reviewer's inference; **unknown** = could not be settled from the documents. Every numbered claim in sections 1, 2 and 5 carries one of these labels.

**Source limitations (observation).**
- This is an internal methodological review. No literature review, no candidate-domain search and no benchmark were performed, by instruction.
- First-party documentation for Cedar, Open Policy Agent (Rego), Common Expression Language (CEL), DMN (via the Camunda engine docs and the DMN TCK), Catala and OpenFisca was consulted to ground section 3.E's baseline ladder. ## 1. Executive verdict

### READY WITH REQUIRED FIXES

**Judgment.** The skeleton is right and should not be redesigned: a micro-workflow as the unit of search; a G0–G2 screen with GO / HOLD / STOP; four same-LLM comparator arms with syntax optional in arm D; preregistration with thresholds fixed in advance; ablations; an append-only decision log; technical and commercial payoffs kept separate; "HOLD is not STOP". No surviving defect requires the owner to rethink that architecture.

**Judgment.** But five clusters of defects would, as written, let the one or two experiments this program can afford produce an uninterpretable or self-confirming result, or let the pass criterion move without any text being edited:

1. "Independent" oracle and "real or synthetic provenance" are never defined relative to the party and encoding that build arm D, so the default solo Claude Code workflow grades D against its own formalization.
2. Preregistration item 4 equalizes information, model and runtime but not development effort, build order or baseline competence, and "where comparable" is unbounded, so arm D wins on attention.
3. Arm D is undefined relative to arm B once syntax is optional, and the LLM's role in each arm is unspecified, so "semantics" is confounded with "structured code" and with "deterministic execution beats LLM judgment".
4. The hypothesis is a four-way disjunction with no primary outcome; G3's "measurable benefit" is not bound to the preregistered threshold or the ablation; thresholds may be set after development results.
5. The indicative thresholds have no statistical form (no base rate, pairing, N, repeat runs or interval), and "critical regressions" and "maintenance effort" are undefined, so at tens of cases GO / STOP is decided by noise in either direction.

Every one of these closes with bounded wording in RESEARCH_PROTOCOL.md (items 1–7, G1, G2, G3) and one sentence in CHARTER.md. None adds a gate, a committee or a new artifact. That is what distinguishes READY WITH REQUIRED FIXES from NOT READY.

**Red-team conclusion (judgment).** The program as written would most likely fail by quietly confirming arm D rather than by killing it prematurely, which is the opposite of the owner's historical error. The reason is structural: every lever that decides the outcome (oracle, baselines, tool choice, thresholds, severity weights, maintenance metric, HOLD duration) is currently held by the party building D. The fixes do not add reviewers; they move each lever to a moment before D exists (preregistration) or to a session that cannot see D.

**Does draft PR #1 need amendments before the owner marks the charter approved?** Yes (judgment). The PR body makes charter approval the trigger for running discovery prompt 01, so every fix that governs the first run must be in the files before the APPROVED entry exists: the oracle class on cards (C01), the G1 expressibility probe and definitions (C07), the discovery channel list and prompt framing (C11), the single card-count rule (C14), the frontier-AI stress-test bullet (C12), and the scorecard anchors (C07). The experiment-stage fixes (C02–C06, C08) must land before the first PLAN.md is approved; landing them in the same amendment commit is cheaper than a second round. Section 6 lists which amendments can wait.

## 2. The five most important defects, ranked by consequence

Consequence scale: 5 = would likely invalidate the program's main conclusion or let goalposts move silently; 3 = would plausibly distort a shortlist or an experiment; 1 = cosmetic. Scores reflect the independent refuters' revised estimates, not the original auditors'.

### Defect 1 (cluster C01, consequence 5, observation) — The reference oracle, synthetic cases and holdout are never made independent of arm D's authors, encoding, or the model's pretraining

**Where.**
- RESEARCH_PROTOCOL.md § Stage 2 — shortlist, G2: "accessible cases, independent truth oracle, fair baseline, legal access, feasible solo implementation."
- RESEARCH_PROTOCOL.md § Experimental preregistration, item 1: "real or synthetic provenance; training/development/test separation."
- RESEARCH_PROTOCOL.md § Experimental preregistration, item 2: "Independent reference answers, qualified human adjudication where needed, uncertainty policy."
- CANDIDATE_TEMPLATE.md: "Potential test oracle and adjudication risks:"

**Failure mode.** "Independent" and "independently" recur across CHARTER and the protocol and are never defined relative to anything. Synthetic provenance is permitted with no constraint on the generator. No adjudicator, qualification, cost or blinding is named. "Training/development/test separation" names a split that does not exist in a program that trains no model. Nothing addresses the shared LLM having memorized the public worked examples that computable oracles are built from. For a solo founder in Claude Code the lowest-effort path is: write the rules once, have the model generate cases and answers from them, encode the same rules as arm D, and have founder plus model adjudicate disputes after seeing arm outputs. D is then scored on agreement with its own encoding (false GO at G3), or memorized answers inflate arm A and compress the D–A gap (the historical "a frontier model already does this" false STOP).

**Minimal correction.** Amendments RP-06, RP-14, RP-15, CT-04. Define three oracle classes at G2 (1 mechanically computable from an authoritative artifact; 2 expert-labeled by a named adjudicator with stated cost; 3 self-labeled by founder or model), with class 3 unable to pass G2 (HOLD). Define independence as: reference answers not authored or labeled by any person or artifact that builds arm D, produced from the authoritative sources alone before D is built and before any arm output is seen, disputes resolved from the source and never from D's specification. Admit synthetic cases only when the generator is not D's encoding or derived from it, with answers from a class 1 or 2 oracle. Replace the training split with development/holdout separation plus a contamination check (perturbed twins with the oracle recomputed, or post-cutoff cases; report perturbed and unperturbed results separately). Record the oracle class and the public-since date on the card. Disclose the class 1 preference as a selection filter in the coverage report.

**Why rank 1 (judgment).** Both this and defect 2 are false-positive routes on the main conclusion, but a circular oracle is invisible to the ablations in item 6, to the logging in item 4 and to any later reader (D simply "agrees with the reference"), whereas effort asymmetry leaves token and time logs that a later reader could use to discount the result. It is also the earliest-binding defect: G2 is screened during the discovery run that approval triggers, so the oracle class must be on the card before a shortlist exists.

### Defect 2 (cluster C02, consequence 5, observation) — Development effort, build order and baseline competence are outside the equality list, so arm D wins on attention and ordering

**Where.** RESEARCH_PROTOCOL.md § Experimental preregistration, item 4: "Same information budget, model access, runtime/tool conditions where comparable. Log exceptions, token/time/cost budgets and retries."

**Failure mode.** Item 4 equalizes information, model and runtime only. "Where comparable" is an unbounded exception judged by the arm-D builder after the fact. Budgets are logged, not equalized or preregistered. The founder designs D, iterates it many times on development cases, and builds B once and C from unfamiliar tooling without reading the incumbent's documented idioms. Nothing freezes B and C before D is implemented or forbids revising D after seeing their results. The item 6 ablation operates within D and cannot see that B and C were under-built. The resulting gap is reported at G3 as a semantic advantage.

**Minimal correction.** Amendment RP-18. Same source documents, pinned model snapshot and runtime conditions, with any unequalizable condition logged in PLAN.md before holdout together with its expected direction of bias. An equal preregistered implementation budget per arm (agent tokens or turns and wall-clock). The same LLM agent with identical instructions, differing only in the named target representation, implements every arm; the owner reviews but does not hand-edit any arm. B and C are built following the incumbents' own documentation, tuned only on the development set, and frozen by commit hash before D is implemented. Record build order; after the last arm is built, give every other arm one equal catch-up round from the same failure list, then freeze all arms. D is not revised after any arm's holdout results are seen. Development effort on B and on C must each be at least that spent on D, or the shortfall is logged and reported with the result. Before scoring, make one documented attempt to fix each baseline failure class by ordinary configuration or idiomatic use of that tool; failures fixed that way do not count toward D's advantage.

**Why rank 2 (judgment).** The refuters kept this at consequence 5 as the single most probable route to a false positive. It outranks defect 3 because effort asymmetry produces a false positive even after arm D and the LLM roles are properly defined, and it is the one confound the existing ablation clause cannot detect.

### Defect 3 (cluster C03, consequence 5, observation) — Arm D is undefined relative to arms B and C, and the LLM's role in each arm is unspecified

**Where.**
- RESEARCH_PROTOCOL.md § Experimental preregistration, item 3: "D. same LLM + proposed semantics (DSL syntax OPTIONAL)."
- prompts/02-adversarial-review.md item 6: "(A LLM/tools; B LLM + structured code; C best incumbent rules engine/DSL; D proposed semantics)"

**Failure mode.** With syntax optional, no document states what D contains that B ("same LLM + structured schema/JSON + ordinary code") lacks or that C does not already provide, and item 6's ablation list names prompts, tools and retrieval but not ordinary code. No arm states whether the LLM authors the artifact from sources, extracts structured inputs, decides at runtime or applies amendments; in A the LLM necessarily decides, while in B, C and D the artifact can execute deterministically. The natural solo build (D executes deterministically against a B that lets the LLM fill a schema at runtime, or D as the more carefully engineered program) yields a correctness gap that is "deterministic execution beats LLM judgment" or "structured code wins", written up as "semantics". Prompt 02, which drafts the preregistered design, drops "same LLM" from C and D, so the two documents define different experiments.

**Minimal correction.** Amendments RP-17 and P2-02. The plan names the construct(s) D adds that B lacks and C does not already provide (an enforced invariant, a typed effect or rule-version rule, a solver or checker call, or similar) and states that D with those constructs removed is B; the D-versus-B difference measures semantic value and the D-versus-C difference measures novelty over existing engines. For every arm, PLAN.md states the LLM's role at each stage (rule author from sources, input extractor, runtime decider, maintainer); roles, budgets and instructions are identical across B, C and D except for the named target representation, and any role difference is itself part of the mechanism under test and must be named before implementation. The primary contrast is D versus the better of B and C; D versus A alone is a floor check, not a result. Restate the four arms with "same LLM" in prompt 02.

**Why rank 3 (judgment).** A confounded contrast cannot be repaired by any threshold or statistical rule, so it outranks defects 4 and 5. It sits below defect 2 because G1's "explicit domain-specific semantic primitive" and prompt 02 item 3's counterexamples already bound what D is meant to add, even though they do not enforce the implementation boundary.

### Defect 4 (cluster C04, consequence 4, observation) — The success criterion is unanchored: disjunctive hypothesis with no primary outcome, G3 "measurable benefit" unbound to the preregistered threshold and ablation, thresholds fixable after development results

**Where.**
- CHARTER.md § Central falsifiable hypothesis: "can materially improve at least one of (a) decision correctness, (b) adaptation to changes in authoritative rules, (c) verifiability, or (d) total cost of implementation and maintenance, without unacceptable trade-offs, versus the best viable baseline."
- RESEARCH_PROTOCOL.md § G3: "GO only if the new semantic mechanism adds measurable benefit on the preregistered task beyond the strongest fair alternative and the effect plausibly generalizes within that narrow domain."
- RESEARCH_PROTOCOL.md item 7: "Threshold for continuation and kill conditions fixed before seeing holdout results." and the indicative paragraph's "Adjust thresholds only before experiment by recorded owner decision."

**Failure mode.** "At least one of" four outcomes with no designated primary lets whichever sub-result moved count as confirmation; only (a) and (b) ever receive indicative thresholds; (c) verifiability moves almost automatically for any explicit representation against an LLM-only arm; "without unacceptable trade-offs" is undefined. G3 never references item 7's threshold or item 6's ablation, so a small full-pipeline delta from validators, retrieval or retry loops present only in D can be a GO without contradicting any sentence. "Before seeing holdout results" and "before experiment" leave a window, after development-set runs, to set the threshold where D already lands. "Material error", "critical regression", "plausibly generalizes" and "meaningful incremental advantage" are never defined. This is the cluster that lets goalposts move without any text being edited.

**Minimal correction.** Amendments CH-01, RP-21, RP-22 (freeze wording), RP-23. Replace the hypothesis sentence with one that names ONE primary outcome per preregistered plan from (a)–(d), with regression limits on the other three fixed in the same plan, versus the strongest fair alternative; the program-level thesis is tested only through per-candidate instances, and improvement on a non-primary outcome does not confirm it; keep the following "The hypothesis is NOT…" sentence verbatim. Bind G3 GO to the effect attributable to the semantic mechanism (every non-semantic component of D either present in B and C or removed in a preregistered ablation whose result is the one scored) meeting the threshold preregistered in the approved PLAN.md against the better of B and C, holding on the preregistered holdout of the same micro-workflow. Fix thresholds, kill conditions, severity weights and the task's written definitions of "material error", "critical regression" and the generalization check in PLAN.md before any arm is implemented or run.

**Why rank 4 (judgment).** Silent goalpost movement is a category the task names as disqualifying regardless of score. It ranks below defects 1–3 because item 7 and "no retroactive success criteria" already make the outcome choice pre-declared rather than post hoc (the refuters' reason for lowering it from 5 to 4), and above defect 5 because the statistical form of a threshold only matters once there is a single anchored criterion to apply it to.

### Defect 5 (cluster C05, consequence 4, mixed observation and judgment) — The indicative thresholds have no statistical form, and "critical regressions" and maintenance effort are undefined

**Where.** RESEARCH_PROTOCOL.md § Experimental preregistration, indicative paragraph: ">=30% reduction in material errors OR >=50% reduction in rule-change maintenance effort against the strongest baseline, with no critical regressions and credible unseen-case generalization." Items 5 ("implement/update effort") and 6 ("Holdout cases, negative controls, ablations…").

**Failure mode (judgment on the arithmetic, observation on the text).** A 30% relative reduction against an unstated baseline error rate, with no requirement that arms be scored on the same cases, no minimum N or per-stratum count, no repeat runs for nondeterministic arms and no interval rule, is one to a few discordant cases when the baseline errs on 5–10% of dozens of cases; the G3 call is then noise in either direction, and two noise-driven nulls end the program under stopping condition (iii). "No critical regressions" has no definition or referent and is asymmetric: a single critical event kills D while baselines with three pass, or the rule is waived informally. The 50% maintenance route can carry a GO alone, yet "effort" has no unit, so lines changed by a terse notation (syntax) stands in for maintainability (semantics), and the founder who designed D edits it faster than an engine they have never used.

**Minimal correction.** Amendments RP-22, RP-19, RP-20. Paired design (all arms on the identical holdout set); a preregistered number of repeat runs for nondeterministic arms with the aggregation rule fixed before holdout; "strongest baseline" defined per metric as the best of A–C; PLAN.md states the strongest baseline's development error rate, the holdout N, and the acceptance form (point estimate meets threshold AND the lower bound of a preregistered paired interval exceeds zero); severity weights and "material" fixed before holdout; if correctness is underpowered at the obtainable N, say so and preregister adaptation as primary. Replace "no critical regressions" with a comparative rule (D's critical-severity failure count not exceeding the strongest baseline's; a critical class unique to D triggers HOLD with the additional cases needed stated). Measure maintenance effort on at least N preregistered rule-change scenarios applied to every arm by the same agent from the same amendment text under the same budget, scoring post-change correctness with no regression first and agent effort second; report lines changed, never score it. Require a per-stratum case count and a detectability statement in item 6, with an underpowered run counting as a pilot that can yield HOLD but not GO.

**Why rank 5 (judgment).** It decides GO / STOP by noise on every experiment the program can afford, in both directions, so it outranks the comparator-set cluster (C06), whose omission of arm C is at least visible in an owner-approved PLAN.md, and the G1 cluster (C07), whose false positives are eventually exposed by arms B and C at the cost of experimental budget rather than a wrong verdict.

## 3. Dimension-by-dimension findings (A–J)

Each subsection gives the verdict for that dimension, then observations, judgments and unknowns. Proposals in this section are proposals; the binding text changes are in the amendments file.

### A. Thesis coherence

**Verdict (judgment):** repairable with small edits; the documents name the object under test at least five ways and fix it nowhere.

**Observations.** The object is called "a new programming language" (repo description; CHARTER Mission "potentially expressed as a new programming language"; G3 "STOP the custom language hypothesis"), "a domain-specific representation and execution model" (CHARTER hypothesis), "a reusable semantic/execution primitive" (payoff 2), an "AI-driven software" advantage (prompt 01 research question), "a narrow workflow product" (payoff 1), and a startup (G4). Every experimental arm is "same LLM + X", so the thesis actually tested is conditional on an LLM-in-the-loop stack. Arm D is "DSL syntax OPTIONAL", so a positive G3 result may be a library.

**Judgment.** The object actually under test is a domain-specific representation (typed inputs, enforced invariants, rule-version or temporal applicability, explicit decision outputs) with a deterministic evaluation or checking procedure, used as a component inside an LLM-assisted pipeline and compared against the same pipeline using other representations: a semantic kernel or checked intermediate representation, not a concrete-syntax language and not a product. Readings 1–3 (language, kernel, LLM-authoring target) become coherent once one primary outcome is named (CH-01), D is defined relative to B (RP-17), the LLM's role is fixed (RP-17), and a G3 GO is scoped to the mechanism (RP-23). Readings 4–5 (product, startup) are the drift paths; the two-payoff split and G4 contain them if G4 gets an outcome set (RP-24).

**Unknown.** Whether the owner intends the LLM to be a required component of any resulting artifact or only the founder's build aid. This decides which comparator counts as the "strongest practical alternative" and is owner decision 1.

### B. Anti-drift effectiveness

**Verdict (judgment):** the intent is unusually strong for a first draft, but the operative word at almost every decision point is undefined, and the process is heavy where it buys nothing.

**Loopholes (observation; enabling text quoted).** HOLD at G0–G2 needs "dated rationale and reopening evidence" but no resolving step, review date or cycle-close disposition, so an all-HOLD cycle either never ends or triggers stopping condition (i), whichever the founder's mood favors. Condition (iii) "two fair experiments fail to show a meaningful incremental advantage" leaves "fair" and "meaningful" to whoever writes the report. Condition (ii) "no plausible new semantic invariant survives comparison with existing engines" has no stage, actor or test. "Stop or redesign the search" makes redesign always available; "Explicit owner approval is required for an additional cycle" has no cap. "Four comparators where feasible" and "where comparable" are judged post hoc by the arm-D builder. "Adjust thresholds only before experiment" and "fixed before seeing holdout results" permit setting the threshold after development runs. "without unacceptable trade-offs" and "no critical regressions" are undefined rescue or kill levers. CLAUDE.md forbids modifying "frozen criteria" but nothing in any file is ever marked frozen. "and major pivots" qualifies a principle that elsewhere reads "No self-authorized pivot".

**Too heavy (observation and judgment).** "Human owner approves gates" read against "Screen every candidate" nominally makes a non-specialist the approver of up to ~90 per-candidate verdicts that will be rubber-stamped, which protects nothing. "Append decisions to DECISION_LOG.md" applied per candidate duplicates the card's own rationale fields and buries the handful of owner decisions the log exists to make auditable. The competition rule, the no-fabrication rule, the no-edit rule and the observed/inferred/assumed rule each appear in five files in different wording with no precedence clause; each stale copy is a candidate for silent divergence.

**Fixes.** Tightening: RP-07 (HOLD), CH-08 (stops), RP-21/RP-22 (freeze point), RP-16 (arms), DL-01 (frozen = Status APPROVED vN). Loosening: CH-07 (five approval points; per-candidate verdicts are agent proposals), RP-25 (one ledger per phase), CL-01 (precedence clause instead of de-duplication). Net: about six added sentences, two removals of process; no new file, role or review step.

### C. Selection bias

**Verdict (judgment):** neutrality is stated three times and every operative mechanism tilts toward domains with public rule text, public worked examples and documented incumbents.

**Observations.** The Stage 1 channel list is "operational manuals, regulations, standards, examples/contracts, GitHub issues, practitioner complaints, open-source code, vendors, buyer evidence": most are rule text or developer/vendor channels, and none surfaces outcome-shaped evidence (incident and recall reports, inspection and enforcement findings, public datasets, tenders, trade-body material). The unit of search has a "governing rules" slot. The only named incumbent class is "DSL/rules engine". The heaviest weight is "Economic value / existing spending", visible only where a budget line or incumbent exists. The only diversity requirement counts industry labels, which six text-rule industries satisfy. "Allow domains outside telecommunications, finance, legal/governance, and enterprise software to rank highly" is permission with no check. Discovery is one prompt, one model, one framing, with blind spots self-reported by the same run. G2's "feasible solo implementation" and "accessible cases" are legitimate constraints of this founder that act as unacknowledged filters.

**Classes the mechanisms systematically miss (judgment, illustrative only; not researched or scored).**
1. Physical-constraint operations (manufacturing tolerance stacks, compounding and lab protocols, food-safety critical limits, agricultural withholding windows, hazardous-material segregation): primary invariant is units, compatibility, mass or energy balance, critical limits; oracle is measured outcome, SOP conformance or incident record. Missed because no SOP, incident, recall or dataset channel exists and the comparator is a rules engine rather than a unit or constraint library.
2. Scheduling, rostering, dispatch and load planning: invariant is capacity, time windows, precedence, qualification coverage; oracle is constraint feasibility against historical schedules or a simulator. Missed because the strongest incumbent is a constraint or MIP solver, the cost shows up as overtime and idle assets rather than software spend, and a non-specialist will judge solver-backed implementation infeasible at G2.
3. Provenance, authority and chain-of-custody (clinical-trial data handling, evidence custody, traceability, maintenance records, grant compliance): worked examples are private, so accessibility and verifiability penalize twice, while audit and enforcement findings, often public, are absent from the channel list.
4. Text-rule domains with private adjudications (insurance claims, building-code inspection, accreditation, benefits casework, customs disputes, payroll and labor rules): the program's natural strength in rule text plus effective dating, but G2's oracle test fails them while regulation, tax and tariff domains with published rulings pass.
5. Low-visibility practitioner domains (trades, agriculture, small clinics, local-government operations, officiating, education administration): practitioners do not write GitHub issues; "existing spending" is low because tools are spreadsheets; "competitive opening" cannot be demonstrated with no incumbents.
6. Spatial and physical-safety domains (site clearances, slotting, segregation distances, ground operations): geometry and adjacency invariants, simulation oracles, GIS/CAD incumbents, none of which the documents anticipate.

**Judgment on compounding.** The funnel's entry (channels), middle (unit of search, comparator class, oracle framing) and exit (20% existing spending, 10% competitive opening, 35% re-scoring of G2 criteria) all point the same way, so the bias compounds. Stopping conditions (i) and (ii) would then be evaluated on a skewed pool facing the strongest incumbents (rules engines, policy languages), a program-level false negative.

**Cheapest corrective set (proposal).** Measure the split by primary invariant class on every card and in the coverage report, with a conditional owner-decided second framed pass (RP-03, CT-05); extend the channel list (RP-01); replace the sector-naming charter sentence with a sector-neutral principle (CH-03); remove the sector lists from prompt 01 and name non-rule-text invariant classes as counting equally (P1-02, P1-03); anchor the two scoring categories (RP-09, RP-10); accept the class 1 oracle preference as a disclosed filter (RP-06). A quota was considered and rejected: it invites padding against "never fabricate breadth".

### E. DSL necessity

**Verdict (judgment):** the principle is stated five times and operationalized nowhere; the question must be split into "does the mechanism add value" (G3) and "does a surface language add value over a host-language embedding of the same mechanism" (a later, separate test).

**Observations.** CHARTER: "Test the value of semantics, types, constraints, execution, and verification — NOT aesthetics of syntax"; "No claim that our mechanism is proprietary or defensible merely because its syntax is new". CLAUDE.md: "Distinguish novel syntax, novel semantics, and operational integration." None of the three terms is defined. Arm D is "DSL syntax OPTIONAL"; G3 is silent on what a GO validates.

**Definitions (proposal, RP-05).** Novel syntax = a new notation for a guarantee an existing alternative already provides as a documented feature. Novel semantics = a named mechanism class (static check, runtime invariant, effective-dated versioning, precedence resolution, provenance, units, totality, formal analysis, change propagation) that the strongest existing alternatives cannot provide, or can provide only by per-use re-implementation, shown by at least one concrete case per alternative. Operational integration = value from connectors, UI, data or deployment, not from the representation. Rule of thumb: documented feature = notation (score 1); per-use re-implementation = library-sized mechanism (score 3; technical payoff possible, language unlikely); cannot provide at all, shown by counterexample = 5.

**Decision table (judgment from background knowledge, unverified in this review, except rows marked †, which are supported by first-party GitHub documentation read 2026-10-12).**

| Mechanism type | Existing tool class that plausibly provides it | Evidence that would show insufficiency |
|---|---|---|
| Static checking (shape, type, unit, schema) | Typed host languages; JSON Schema; Cedar schema validation†; CEL type checking†; DMN table validators† | A preregistered corpus of real domain errors that pass every baseline static check and are caught by the proposed check, plus a showing that the host type system cannot express the check soundly or without per-use re-implementation |
| Runtime invariant enforcement | Database constraints and triggers; validator libraries; design-by-contract; OPA admission control† | An invariant spanning multiple steps, documents or times such that baseline check points are necessarily local |
| Effective-dated rule versioning | Bitemporal SQL; versioned policy bundles; versioned DMN/Drools knowledge bases; OpenFisca dated parameters and reforms† | On a preregistered amendment set, a bitemporal question B and C answer wrongly or only with ad hoc code; edit sites and effort per arm |
| Authority and precedence resolution | Cedar forbid-overrides-permit†; Rego default and conflict detection†; Drools salience; DMN hit policies†; Catala prioritized default logic for exceptions† | A conflict set whose domain precedence is a partial order that engines flatten to a scalar priority, producing wrong answers or per-rule encoding of the order |
| Provenance and source-cited explanation | Rego trace; Cedar determining-policy diagnostics; audit logs; Catala literate pairing with statute† | Baseline traces reference internal rule ids rather than source clause and version, and cannot be reconstructed after an amendment |
| Units and mandated rounding | Units-of-measure libraries and types | Domain quantities with non-standard algebra producing reference-case mismatches in B and C |
| Totality and exhaustiveness | Exhaustiveness checking in ML-family languages; DMN completeness and overlap analysis† | Gaps or overlaps on enumerated or fuzzed inputs that baseline analyzers miss because the domain partition is not a product of enumerated types |
| Formal analysis (equivalence, reachability, conflict freedom) | Cedar symbolic analysis†; Rego tests†; SMT and model checkers; constraint solvers | A decidable domain question general tools cannot answer in bounded time or without re-encoding the domain per question |
| Change propagation and amendment impact | Build systems; incremental Datalog engines; spreadsheets | Baseline dependency graphs report impact incompletely on a preregistered amendment set |
| Sequencing, retries, compensation | Workflow engines (BPMN, durable execution) | Rarely; a sequencing primitive should treat the workflow engine as arm C and will seldom justify a language |

**Baseline ladder (proposal, RP-12; first-party characterizations from GitHub docs read 2026-10-12, limitations in section 0).** (1) Typed data plus ordinary code in a typed host language (arm B). (2) An embedded, terminating expression language over typed data: CEL, which its specification describes as side-effect-free, terminating and not Turing-complete. (3) A general declarative policy engine over arbitrary structured data: OPA Rego, whose docs describe compile-time conflict and recursion rejection, optional schema type checking and a test framework. (4) A domain-shaped policy language with proven analysis: Cedar, whose docs describe fixed permit/forbid semantics with default deny, schema validation with a soundness proof, and symbolic analysis; applicable only to authorization-shaped primitives, otherwise the benchmark for what a mature narrow DSL plus verification already delivers. (5) A standardized decision-table engine: DMN via Camunda or Drools, with hit-policy semantics and TCK conformance. (6) A rules-as-code computation framework for quantitative legislation with dated parameters and reforms: OpenFisca. (7) A law-to-code DSL with formal semantics and prioritized exceptions: Catala. (8) Constraint, SMT and optimization solvers and formal-spec tools (background knowledge, not fetched). Arm C is the strongest rung whose domain shape matches the candidate, with first-party citation; if the strongest alternative is rung 1 or 2, arm B must be built with it.

**Fair-comparison procedure (proposal, RP-18 and RP-17).** Adversarial review names the ladder rung and product for C and writes a one-page best-practice encoding of the primitive in B and in C from the incumbents' own documentation. B and C are implemented first, tuned on the development set to a preregistered stopping rule, frozen by commit hash; only then is D described and built. Same pinned model, tool access, token, wall-clock and iteration budget per arm; the same agent implements every arm; every human edit is logged per arm. A separate agent reviews B and C against the incumbent docs for straw-manning before holdout. Reference answers exist before any arm sees a case. Ablations: D-minus-primitive (D's scaffolding with the mechanism disabled), and a negative-control task with no expected semantic gap on which D should not win. Record that the agent is far more fluent in Python, SQL and Rego than in any new notation; this biases against D-as-syntax and is a further reason the G3 test is mechanism-level, with the surface-language question deferred to a separate test whose benefit is stated in advance (non-programmer authoring, static checks the host cannot express). A G3 GO is recorded as "mechanism M improves metric X by Y against ladder rung R on task T with holdout N", never as "a language is needed".

### F. Evidence feasibility

**Verdict (judgment):** 20–30 table rows are attainable in one deep-research run; 20–30 full cards with verifiable per-claim citations are not; ten cards are. Oracle construction is realistic only for class 1 oracles.

**Observations.** CHARTER targets "20–30 credible micro-workflows"; RESEARCH_PROTOCOL Stage 1 says "For each candidate use research/01-discovery/CANDIDATE_TEMPLATE.md"; prompt 01 asks for a 20–30 row table (B), ten cards (C) and a G0/G1/G2 screen (D) without stating which set D screens. Stage 1 requires per claim "link, access date, applicable publication/version date, quoted or paraphrased source observation, and confidence". Preregistration item 2 says "qualified human adjudication where needed" and names no one. Item 1's "training/development/test separation" is the only leakage language and does not address pretraining contamination. Nothing constrains synthetic case generators.

**Judgments.** Deliverable B's weakest cells will be "accessible validation" and "source links", where hallucinated or paraphrased citations concentrate. Screening 10–20 uncarded rows at G1/G2 is unsound; they should be marked "discovered — not carded", never STOP, and not counted toward stopping condition (i) (RP-02, RP-04, P1-04, P1-05). The founder can verify a handful of citations per card, not all; verification should be scoped to finalists' G0 links and the citations behind semantic-advantage scores of 4–5 (RP-11). Class 1 oracles (official calculators, reference implementations, conformance suites, published worked answers with errata, adjudicated decisions with reasoning) are the only kind this founder can afford; class 2 needs a named person and budget; class 3 (founder or model labels) is self-grading and should fail G2 (RP-06). This preference tilts the portfolio toward codified domains and must be disclosed in the coverage report rather than operate as a hidden filter.

**Controls to require in preregistration (proposal, RP-14, RP-15, RP-20).** Development/holdout separation with every case used to build any arm listed and excluded from holdout. Perturbed twins of every public case with the oracle recomputed (feasible only with a class 1 oracle). Post-cutoff cases whose governing rule became effective after the model's stated training cutoff, especially for the temporal-amendment stratum. A canary: keep the unperturbed public cases and compare arm A on verbatim versus perturbed items; report with and without. Synthetic generator never D's encoding or derived from it; synthetic answers from a class 1 or 2 oracle; synthetic share declared per stratum; a synthetic-only holdout counts against "credible unseen-case generalization". Per-stratum counts (normal, exception, conflict, temporal amendment, missing data, adversarial) and a detectability statement.

### G. Experimental validity

**Verdict (judgment):** the four-arm skeleton is right; as written it cannot isolate the semantic contribution.

**Observations.** See defects 2, 3 and 5. In addition, item 6 names the goal ("ablations to isolate benefit from semantics vs prompts/tools/retrieval") but no concrete ablation, and omits "ordinary code" from the list; "severity-weighted" correctness in item 5 is not required to be fixed before results.

**Judgment on the thresholds.** A relative threshold without a base rate is not a threshold. If the strongest baseline's material-error rate on development cases is p, a 30% relative reduction is 0.3p absolute; with p at 5–10% and dozens of cases that is one to a few discordant pairs. The protocol should require PLAN.md to state p, the holdout N, and the smallest effect that N can separate from noise, and to declare correctness underpowered a priori (and adaptation primary) when it cannot (RP-20, RP-22). "No critical regressions" should become comparative (RP-22). Maintenance effort should be measured as post-change correctness with no regression per unit of same-agent effort, with lines changed reported but never scored (RP-19).

**Revised preregistration sketch (proposal, not an approved design).** Arms: B (same LLM authors typed schema plus code), C (same LLM authors rules in the engine chosen by the baseline ladder), D (same LLM authors the proposed semantic artifact, syntax optional), and D-null (D with the semantic mechanism disabled, everything else identical; nearly free as a flag). A (same LLM plus tools and documents, no authored artifact) is run with an untuned prompt as a floor and negative control, never as the baseline that decides GO. Roles identical across B, C, D: author = same agent, same instructions, same budget, founder reviews but does not hand-edit; extractor = shared pre-structured case inputs; decision = deterministic execution of the artifact (the LLM decides only in A); maintainer = same agent applies each preregistered rule-change scenario under the same budget. One stratified holdout never seen by the author agent; every arm on every case; nondeterministic arms run a preregistered number of times with a fixed aggregation rule. One primary endpoint declared in advance. GO requires: point estimate meets the preregistered threshold against the best of A–C on that metric; lower bound of a preregistered paired interval above zero; D's critical-failure count not above the strongest baseline's with no critical class unique to D; D beats D-null with D-null outside D's interval. Kill rule: D below a preregistered minimum relative improvement, or D-null within D's interval (the gain is tooling or prompting; the domain product may still be interesting). HOLD only for a named missing fact, typically "underpowered", with the extra case count stated. The arm that matters most for DSL necessity is C; dropping B or C loses the distinction between semantics, structured code and incumbent engine, so neither should be droppable by "where feasible" (RP-16).

### H. Economics and go-to-market

**Verdict (judgment):** the separation principle is stated correctly and placed correctly (buyer evidence after G3; nothing forces interviews before a small experiment); it is not operationalized.

**Observations.** CHARTER "Keep these evaluations separate. A technical success is not automatically a startup." G4: "Evaluate technical result and buyer/distribution evidence separately… Do not claim market validation from benchmark success." Payoff 2 ("independently reproducible, reusable semantic/execution primitive") has no test; G4's "actual payer" is undefined and G4 has no outcome set; the charter's "portfolio decision" has no home; G3's "A domain product may remain interesting without a DSL" has no destination. The 20% "Economic value / existing spending" and 10% "Demonstrable competitive opening" categories have no evidence standard, and the former favors concentrated enterprise spend over diffuse cost.

**Two-ledger separation rule (proposal, CH-02, RP-24).** Technical ledger: G3 GO on the approved PLAN.md; reproduction of the effect from the published plan, data and code in a clean session or by a party that did not build it; "reusable" claimable only after application to a second small case set from a different workflow in the same domain, otherwise "reusability untested"; adoption not required; a technical payoff with no buyer is a valid end state. Commercial ledger, tier 1 (discovery and adversarial review, public sources only): incumbent public pricing, job postings for the operator role, regulator penalty or enforcement data, procurement contract values, vendor count, complaint or issue volume, with buyer concentration recorded beside the economic score; tier 1 establishes that value exists and never establishes willingness to pay. Tier 2 (after G3 GO only): dated recorded responses from at least N operators in the target role who have seen the G3 result, logged as stated intent not payment; a route to delivery this founder can execute; unit economics computed from buyer-side figures, never from the experiment's own implementation effort or token cost. Join at G4 as exactly one of STARTUP / OPEN-SOURCE RELEASE / NON-DSL PRODUCT LEAD (logged, passes no gate, pursued only via charter amendment) / SHELVE; if operators cannot be reached within the owner-set window, the outcome is OPEN-SOURCE RELEASE or SHELVE, not an open HOLD.

### I. Resource discipline

**Verdict (judgment):** the weakest dimension of an otherwise careful draft.

**Observations.** CHARTER § Scope and timebox contains counts (20–30, >=6, up to 5, up to 2) and no calendar duration, owner hours or spend figure; no such figure appears in any of the nine files, so "budget extensions" and the protocol's "cost so far" have no referent. The binding constraints for a solo non-specialist are the owner's reading time for five adversarial reviews and the engineering of arm C (an unfamiliar mature engine) and arm D. **Program-level kill criteria (proposal; each an owner decision to adopt or amend; CH-08).** Candidate STOP (per domain): G1 STOP under the probe; G3 STOP when D fails to beat the better of B and C on the primary metric or ablations attribute the gain to retrieval, tools or prompting. REDESIGN the search (at most once per program): a cycle yields no G0–G2 candidate AND the coverage report shows a method defect (industries or source classes unreached, run cut off). Not sufficient for an extension: "more candidates probably exist", a frontier-model release, enthusiasm for a syntax, or a finalist attractive only because sources are thin. Sufficient: a preregistered experiment at or above threshold with ablations not attributing the gain elsewhere, funding replication; or a HOLD naming a single missing fact at a bounded, stated cost.

**Caps the owner should set (ranges are judgment, not evidence; CH-06).** Finalists 3 (range 2–4) or the drafted 5. Experiments per cycle 2, on different candidates unless the first shows a positive primary-metric effect that needs replication. Discovery cycles at most 2 before program STOP (a). Calendar: discovery plus screening a few weeks; adversarial review of three finalists a few weeks; each experiment several weeks including oracle construction; the first cycle plausibly a few months at part-time effort. Owner time: a weekly hours figure. Spend: per discovery cycle, per experiment and program total, derived from what the owner is willing to lose on a null result. No currency or hours figure is proposed; inventing one would be fabricated evidence.

## 5. Revised minimal gate architecture (PROPOSAL, not a rewrite)

**Observation.** The current architecture is: Stage 1 discovery; Stage 2 screen with G0 (real outcome gap), G1 (language plausibility), G2 (testability), each GO / HOLD / STOP per candidate; an unnumbered weighted scorecard; an unnumbered adversarial review of up to five finalists; an unnumbered owner-approved preregistration in experiments/[candidate]/PLAN.md; G3 technical result; G4 strategic result with no outcome set; charter stopping conditions (i)–(iii); "Human owner approves gates, changes to charter, test design, budget extensions, and major pivots."

**Judgment.** It is both overcomplicated and under-specified, in complementary places, with one root cause: approval and record-keeping sit on the wrong unit (the candidate) while the units that carry drift risk (what an approval is, HOLD, the G3 claim, the program stop, the frozen set) are undefined. Overcomplicated: up to ~90 nominal per-candidate owner verdicts; five full adversarial reviews and five four-arm designs feeding two experiments; one phase outcome written into up to four artifacts under three names; a card for every candidate; core rules restated in several files. Under-specified: no definition of approval; HOLD without expiry; thresholds adjustable after development results; droppable arm C; a G3 GO unscoped between "the mechanism helps" and "a language is needed"; G4 without outcomes; one discretionary stop sentence; "frozen" with no referent.

Everything below is offered for the owner to accept, amend or reject in parts. Gate names G0–G4 and the GO / HOLD / STOP vocabulary are kept. The proposal changes who decides what, where it is recorded, when it binds, and what ends the program. The corresponding minimal text changes are CH-07, CH-08, CH-06, DL-01, RP-07, RP-23, RP-24; a parameter register is optional (see 5.6).

### 5.1 Two decision classes plus one exception class

Silence at the approval point ratifies the batch. Nothing binds by time passing. |

### 5.4 HOLD wherever it appears

Every HOLD carries the missing fact(s), the bounded step that would obtain each with its estimated cost, and its expiry, which is always the next routine approval point. At expiry the item becomes PARKED with reopening evidence equal to the named fact. PARKED is not STOP (reopenable without a charter change; never a failure finding) and is not satisfied (does not count toward the shortlist, toward GO, or against the program stops). STOP always names reopening evidence, as today.

### 5.5 Stop criteria at three levels

| Level | Trigger | Outcome | Decided by |
|---|---|---|---|
| Candidate (per domain) | G1 STOP under the probe; G2 PARKED; G3 STOP-MECHANISM | That domain's language thesis stops; the program continues | Agent records; owner ratifies at the next point |
| Search (method) | A cycle ends with no G2 GO AND the coverage report shows a named method defect | REDESIGN: one further cycle with a documented change of sources or framing; at most once per program | AX |
| Program | P1 two independently framed cycles yield no candidate with G1 GO and G2 GO on a class 1 or 2 oracle. P2 two experiments that met their preregistered N, on different candidates, both STOP-MECHANISM (or one plus its preregistered replication). P3 any cap reached without a GO-MECHANISM. P4 a GO-MECHANISM is recorded: the program closes as a success through A4; continuation is a new charter version. | CLOSE at A4; reopening only on new external evidence logged | Owner at A4 |

Underpowered pilots count toward the experiment budget but not toward P2.

### 5.6 Frozen parameters and the decision log

"Frozen" means: the Status line of CHARTER and RESEARCH_PROTOCOL reads APPROVED vN date, plus the text of every approved PLAN.md (DL-01). Frozen text changes only by an entry that shows before and after and bumps the version. Optionally (owner's call) a one-page PARAMETERS.md or protocol appendix lists every number and rule the program depends on (candidate target, industry floor, card cap, finalist cap, experiments per cycle, redesign cap, the seven weights, the indicative effects, arm definitions and the LLM-role rule, G1 probe criteria, oracle classes, HOLD expiry, approval points, caps) so a quiet change is a readable diff of one small file. Loggable events: the routine approvals, vetoes, exceptions, G3 records, the A4 outcome, and one phase-end ledger per phase (RP-25). Per-candidate verdicts and scores live on cards and bind only through A2.

## 8. Owner decision checklist (five decisions)

1. **Is the LLM a required component of any resulting artifact, or only the founder's implementation aid?** Options: (a) LLM-pipeline scope for this cycle: arms A–D as drafted, any unrun non-LLM incumbent disclosed and a G3 GO recorded as conditional on it (RP-16); (b) incumbent scope: require a non-LLM incumbent arm whenever one plausibly exists, accepting that most such arms are infeasible for a solo founder and will force HOLDs; (c) decide per candidate at PLAN.md approval. Recommendation: (a) for the first cycle, with the disclosure clause, revisited at the portfolio decision. Why the owner: this fixes what the thesis is about and which comparator counts as "best viable baseline"; an agent choosing it would be selecting the hypothesis it is then asked to test.

2. **What counts as program success, and is one primary outcome per experiment mandatory?** Options: (a) one primary outcome per experiment (CH-01) and either payoff is success, recorded at G4 as STARTUP / OPEN-SOURCE RELEASE / NON-DSL PRODUCT LEAD / SHELVE; (b) one primary outcome but startup is the only success and G4 becomes a kill gate; (c) keep the disjunctive hypothesis and accept the forking-paths risk. Recommendation: (a); it is the only option consistent with "Keep these evaluations separate" and with the anti-premature-kill purpose, and (b) reintroduces the commercial veto the charter was written to avoid. Why the owner: a value judgment about what the founder wants and what risk of a null result they accept.

3. **Budget and scope caps.** Fill CH-06: calendar weeks per cycle, owner hours per week, spend per discovery cycle and per experiment, derived from loss tolerance on a null result rather than expected value. Choose finalists reviewed (3 with two in reserve on HOLD, or the drafted 5). Choose whether the two experiments run sequentially on different candidates with an owner go/no-go after the first holdout (breadth; lets program stop (b) fire) or as one candidate plus replication (depth). Choose whether all four arms are mandatory with an owner-approved exception (RP-16 as drafted) or a three-arm floor (A, D, and the strongest of B/C) is acceptable. Recommendation: fill all four caps before G0; 3 finalists; sequential experiments on different candidates, replication only after a positive primary-metric effect; four arms mandatory with the exception rule, because dropping B or C loses the only contrast that distinguishes semantics from structured code and from an incumbent engine. No currency or hour figure is proposed here because inventing one would be fabricated evidence. Why the owner: only the owner knows their money, time and tolerance for loss.

4. **Scorecard and diversity mechanism.** Keep the 20/20/15/15/10/10/10 weights for cycle 1 (every lens recommended keeping them) or renegotiate now. Confirm the technical reading of "Demonstrable competitive opening" (anchored to incumbent documentation, RP-10) or delete the category and redistribute its 10%. Confirm "Economic value / existing spending" includes loss, rework and workaround labor. Choose the diversity mechanism: (a) a reported split by invariant class with the owner deciding whether to fund a second framed pass (RP-03, CH-03 as drafted); (b) a one-third quota and an automatic second pass written into the charter; (c) industry count only. Recommendation: keep the weights and revisit only by a logged decision after the first published sensitivity scenario; anchor competitive opening technically and publish totals with and without it; adopt (a), because a quota invites padding against "never fabricate breadth" and an automatic second run commits spend the owner has not authorized. Why the owner: PR #1 item 2 reserves weights and search scope to the owner, and the diversity option trades spend against coverage.

5. **Who judges and adjudicates in a solo program.** Who scores the G1 expressibility probes (owner alone; a separately prompted agent session by default with owner spot-checks; a paid reviewer).
